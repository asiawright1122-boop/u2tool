# U2Tool Project Map

Last updated: 2026-07-03

This document is a quick working map of the U2Tool codebase. It complements
`docs/PROJECT_INDEX.md` with a shorter, task-oriented view for maintainers and
agents who need to understand the project before changing it.

## What This Project Is

U2Tool is a multilingual utility-tool site. It renders localized tool pages,
SEO/support content, discovery surfaces, and interactive browser tools.

Production runs as Astro 6 SSR on Cloudflare Workers, with Svelte islands for
tool interactivity.

```text
Request
  -> Cloudflare Worker
  -> Astro middleware
  -> Astro route
  -> BaseLayout
  -> SEO/support content
  -> Svelte island when the page needs interactivity
```

The core domain language is defined in `CONTEXT.md`. The most important rule is
that public pages must never expose internal reasoning traces or agent process
text.

## Runtime Backbone

| Concern | Primary file |
| --- | --- |
| Cloudflare Worker entrypoint | `src/worker.ts` |
| Request normalization, redirects, cache, security headers | `src/middleware.ts` |
| Astro layout and shared SEO primitives | `src/layouts/BaseLayout.astro` |
| Cloudflare/Astro build config | `astro.config.mjs` |
| Worker bindings and routes | `wrangler.jsonc` |

`src/worker.ts` handles legacy build assets and special-cases the AI Discovery
events endpoint before delegating to Astro.

`src/middleware.ts` is the canonical URL policy layer. It handles locale
redirects, legacy route redirects, GSC recovery redirects, trailing slash
normalization, production origin normalization, security headers, HTML edge
cache, and HEAD response conversion.

`astro.config.mjs` configures Astro server output for Cloudflare, copies
`src/messages/` into the build output, injects an HTML cache version from git,
and includes Wrangler/Miniflare repair hooks used by the local/build pipeline.

Current catalog snapshot:

- 557 tools
- 14 categories
- 100 popular tools
- locales: `en`, `zh`, `ja`, `ko`, `es`, `pt`, `fr`, `de`, `ru`, `ar`

`src/config/tools/` stores routing/runtime identity only: slug, category, icon,
component, and popularity. Localized names, descriptions, SEO copy, usage
steps, examples, and FAQs live in `src/messages/`.

`src/lib/translations.ts` is a deep module. It hides bundled imports, filesystem
fallbacks, public asset fetches, English fallback merging, alias handling, and
lighter tool-page loading behind a small API.

## Main Page Surfaces

| Surface | Route file |
| --- | --- |
| Home | `src/pages/[locale]/index.astro` |
| Tools index | `src/pages/[locale]/tools.astro` |
| Tool detail | `src/pages/[locale]/tools/[slug].astro` |
| Category detail | `src/pages/[locale]/categories/[category].astro` |
| Compare hub/detail | `src/pages/[locale]/compare/*.astro` |
| AI Discovery | `src/pages/[locale]/ai.astro` |
| Static info pages | `src/pages/[locale]/privacy.astro`, `terms.astro`, `contact.astro` |
| Machine-readable discovery | `src/pages/sitemap*.ts`, `robots.txt.ts`, `llms*.txt.ts` |

The tool detail route is the densest orchestration point in the app. Its flow is:

```text
locale + slug params
  -> validate locale and tool
  -> load lightweight base UI messages
  -> load current tool page messages
  -> build SEO metadata and structured data
  -> assess support-content trust
  -> build fallback support content when needed
  -> build comparison and cluster cards
  -> render static crawler-visible sections
  -> hydrate ToolWrapper with the Svelte tool island
  -> render FAQ and related tools
```

The dynamic tool island path is:

```text
src/pages/[locale]/tools/[slug].astro
  -> src/components/tools/ToolWrapper.svelte
  -> src/components/tools/ToolImportMap.ts
  -> src/components/tools/<ToolComponent>.svelte
```

`ToolImportMap.ts` is generated by `scripts/generate-tool-import-map.ts`; do not
edit it manually.

## AI Discovery

AI Discovery is deterministic matching, not an external LLM call.

| Concern | Primary files |
| --- | --- |
| Runbook | `docs/AI_DISCOVERY_LAYER.md` |
| UI page | `src/pages/[locale]/ai.astro` |
| Search API | `src/pages/api/ai-discovery/search.ts` |
| Events API | `src/pages/api/ai-discovery/events.ts` |
| Search orchestration | `src/lib/ai-discovery/search-service.ts` |
| Candidate index | `src/lib/ai-discovery/index-builder.ts` |
| Matcher | `src/lib/ai-discovery/matcher.ts` |
| Query normalization | `src/lib/ai-discovery/normalize.ts` |
| Telemetry | `src/lib/ai-discovery/telemetry*.ts`, `events-handler.ts` |

Flow:

```text
query
  -> normalize
  -> load localized tool metadata
  -> build tool and comparison candidates
  -> score candidates by name, SEO text, category, aliases, and intent keywords
  -> return direct / suggest / fallback
  -> optionally record telemetry
```

Scoring thresholds live in `src/lib/ai-discovery/search-service.ts`.

## Operational Scripts

The important script clusters are:

- `scripts/validation/` - production gates and regression checks.
- `scripts/seo/` - GSC and SEO reporting.
- `scripts/tools/` - tool localization, onboarding, and launch.
- `scripts/maintenance/` - health checks and translation maintenance.
- `scripts/planning/` - traceability reports.
- `scripts/ai-discovery/` - telemetry analysis and regression-loop tools.

High-signal commands:

```bash
npm run check
npm run qa:seo-governance
npm run qa:runtime-integrity
npm run qa:ai-discovery
npm run qa:production
npm run verify:production
```

For adding tools, start with:

```bash
npm run tools:launch -- --input path/to/tool-launch-batch.json
```

and read `docs/TOOL_ONBOARDING_WORKFLOW.md`.

## Architectural Hotspots

These areas are important enough to inspect carefully before broad changes:

1. `src/pages/[locale]/tools/[slug].astro`
   - Many concerns meet here: routing, loading, SEO, structured data, content
     trust, fallback content, cluster cards, Svelte island hydration, related
     tools, and layout.

2. `src/components/tools/`
   - This is the largest UI surface. Prefer extracting shared parsing,
     validation, export, and chart/runtime behavior into `src/lib/` before
     duplicating fixes across many tools.

3. `src/lib/*-cluster.ts`
   - Multiple cluster builders share similar shapes. This is a likely
     refactoring seam if cluster behavior needs to change.

4. `scripts/`
   - Production governance scripts and historical one-off scripts are mixed in
     the same tree. Be careful to identify whether a script is a current gate,
     a report generator, or a historical batch helper.

5. `src/messages/`
   - The message corpus is large and has high blast radius. Prefer existing
     validators before manual broad edits.
